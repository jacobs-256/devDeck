# Releasing DevToolBox

DevToolBox ships through GitHub Releases with **signed updater artifacts**, so
installed copies can update themselves.

## One-time setup

Generate an updater keypair (minisign):

```bash
pnpm --filter @devtoolbox/desktop exec tauri signer generate \
  -w .signing/devtoolbox.key
```

- The **public key** goes into `apps/desktop/src-tauri/tauri.conf.json` at
  `plugins.updater.pubkey`. It is embedded in the app, so rotating it requires a
  release signed with the old key first.
- The **private key** is a secret. Store it in the repository secrets:
  - `TAURI_SIGNING_PRIVATE_KEY` — the key file contents (or a path in CI is not
    reliable; paste the contents)
  - `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` — the key password (empty if unset)

`.signing/` is git-ignored. Never commit it.

## Cut a release

```bash
# 1. Bump versions (app + tauri.conf.json share one version)
pnpm version minor --no-git-tag-version
# update apps/desktop/src-tauri/tauri.conf.json "version" too

# 2. Verify
./cli.sh check
pnpm --filter @devtoolbox/desktop build

# 3. Tag and push
git add -A
git commit -m "chore(release): 2.2.0"
git tag v2.2.0
git push origin HEAD --tags
```

`.github/workflows/tauri-release.yml` then:

1. builds macOS (arm64) and Windows (x64) bundles,
2. signs updater artifacts with `TAURI_SIGNING_PRIVATE_KEY`,
3. creates a **draft** GitHub Release with the installers, `.sig` files, and
   `latest.json`.

Publish the draft when the artifacts look right. The app's update endpoint is:

```
https://github.com/XthingsJacobs/devToolBox/releases/latest/download/latest.json
```

Because it uses `releases/latest`, only the newest **published** release is
served to clients.

## Local updater rehearsal

Before tagging, you can exercise the exact updater path without publishing:

```bash
./scripts/updater-rehearsal.sh      # or: pnpm release:rehearse
```

The script builds `target/release/bundle/macos/*.app.tar.gz` with
`createUpdaterArtifacts`, verifies its minisign signature against the public key
pinned in `tauri.conf.json` (via `scripts/verify-updater-artifact.mjs`), and
writes a `latest.json` draft with the GitHub Releases URL and platform key
(`darwin-aarch64`, `darwin-x86_64`, `linux-x86_64`, `windows-x86_64`).

It reads the key from `TAURI_SIGNING_PRIVATE_KEY` or `.signing/devtoolbox.key`
(gitignored). Nothing is uploaded.

## Local signed build

To reproduce CI locally (macOS example):

```bash
TAURI_SIGNING_PRIVATE_KEY="$(cat .signing/devtoolbox.key)" \
TAURI_SIGNING_PRIVATE_KEY_PASSWORD="" \
pnpm --filter @devtoolbox/desktop tauri build --bundles app,dmg \
  --config '{"bundle":{"createUpdaterArtifacts":true}}'
```

Expected output in `target/release/bundle/`:

| Artifact                               | Purpose           |
| -------------------------------------- | ----------------- |
| `dmg/DevToolBox_<version>_aarch64.dmg` | Installer         |
| `macos/DevToolBox.app.tar.gz`          | Updater payload   |
| `macos/DevToolBox.app.tar.gz.sig`      | Updater signature |

`latest.json` is generated by `tauri-action` from these artifacts, not by the
CLI.

## Updating the app

`Settings → Updates` calls `check()` from `tauri-plugin-updater`. When an update
exists, **Install** downloads it, verifies the signature against the embedded
public key, and installs it. The user restarts DevToolBox to finish.

Update checks only work in packaged builds: in `tauri dev` there is no configured
release feed, and the UI surfaces the error.

## Marketplace artifacts are separate

Plugin ZIPs and `registry.json` are signed with the **marketplace** key described
in [Marketplace protocol](marketplace.md#6-integrity-and-signing). Do not reuse
the updater key for plugin artifacts: the two trust roots can be rotated
independently.

### Publish a marketplace release

The `Marketplace release` workflow
(`.github/workflows/marketplace-release.yml`) builds every module, packs and
signs the ZIPs, re-signs `registry.json`, verifies all signatures, and uploads
the assets to a GitHub release. `make_latest` is deliberately `false`, so the
app updater keeps pointing at the newest **app** release.

One-time setup: add a repository secret `MARKETPLACE_SIGNING_KEY` containing the
Base64 Ed25519 seed:

```bash
node marketplace/scripts/sign.mjs keygen --out marketplace-key.txt
# copy the printed "private key (Base64)" value into the secret
```

Then either push a tag:

```bash
git tag marketplace-v1
git push origin marketplace-v1
```

or run the workflow manually with a tag name. Assets published:

| Asset                             | Purpose                                       |
| --------------------------------- | --------------------------------------------- |
| `registry.json` + `.sig`          | Registry document and its Ed25519 signature   |
| `<plugin>-<version>.zip` + `.sig` | Signed plugin packages                        |
| `public-key.txt`                  | Base64 public key to paste into Trust options |

Users add the registry URL:

```
https://github.com/<owner>/<repo>/releases/download/marketplace-v1/registry.json
```

For staging or self-hosting, run packing with
`MARKETPLACE_DOWNLOAD_BASE_URL=http://<host>/<path>` instead of a GitHub tag;
`downloadUrl` then points at that base.

## Key rotation

1. Ship a release signed with the current key.
2. Generate a new keypair, publish the new public key in the next app version.
3. After users are on that version, sign future releases with the new key.

There is no way to recover a lost private key: users must install a new build
manually.

## Checklist

- [ ] Version bumped in `package.json`, `apps/desktop/package.json`, and
      `apps/desktop/src-tauri/tauri.conf.json`
- [ ] `./cli.sh check` passes
- [ ] Release draft contains macOS + Windows installers and `.sig` files
- [ ] `latest.json` points at the new version
- [ ] Draft published
